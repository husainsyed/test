▸ what we noticed

the memory footprint
was increasing.

we monitored the system and found that memory footprint was huge compared to the traffic we had.

risk · 01 task manager evictions kubelet starts killing TM pods when the node runs out of memory headroom — work in flight is lost.
risk · 02 job restart loop every eviction forces the JobManager to restart the whole job from the last checkpoint — reprocessing lag compounds.
risk · 03 cluster instability repeated evictions cascade across nodes. eventually the JobManager itself exits and the pipeline goes dark.
root cause — what we found

each TaskManager was sized for 25 GiB. it was actually using ~28.5 GiB.

memory ALLOCATED · per TM 25.0GiB what we declared in the pod spec — the scheduler trusted this number when placing TMs on nodes.
memory ACTUAL · per TM ~28.5GiB what the JVM + state actually needed at peak load. 3.5 GiB more than the request — per pod.

fix applied

three changes — stop stacking, raise requests, drop log volume.

FIX 01 · scheduler

TaskManager count

50→40
reduces cluster-wide memory pressure and stops the scheduler from stacking 4 TMs onto a single node.
FIX 02 · resources

memory request

25GiB→30GiB
requests now exceed real usage. scheduler no longer overcommits the node; limit unchanged at 35 GiB.
FIX 03 · observability

log levels

DEBUG→INFO + WARN
reduces log volume, GC pressure, and the noise that was masking real signals.
